**Date**: 2026-08-02
**Scope**: Full review — product, architecture, retrieval, cost, tests, docs honesty
**Method**: Code reading + **live probing of the deployed dev stack** (12 independent review passes, each adversarially verified)

---

## Executive summary

The capture pipeline is genuinely good. The retrieval layer it feeds — the product's entire value proposition — **has never worked in production**, and the observability that should have caught this is disabled by a missing IAM permission.

Three facts frame everything below:

1. **Semantic search has never run.** Every `/ask` request silently falls back to BM25-only. Verified three independent ways. **[live]**
2. **Nobody was watching.** Five of six metric-emitting Lambdas lack `cloudwatch:PutMetricData`. The dashboard and the `SearchHitCount` alarm built specifically to detect broken indexing read metrics that can never be published. This is the root cause of why #1 survived for months.
3. **Effort went to the wrong layer.** 53% of the last 25 commits' churn went to the galaxy visualization; 11.5% to retrieval. Thirteen consecutive commits on hover orbs and drag physics while the engine underneath was broken.

There are also two **silent data-loss bugs on a clock**: every note self-deletes after 365 days, and notes over 1,000 characters are truncated in the read path.

## P0 — Critical

### 1. Semantic search has never run in production **[live]**

`packages/infra/lib/shared/search.ts:148` attaches the user filter as a **top-level** `filter` key, sibling to `query`:

```js
query: { hybrid: { queries: [ multi_match, knn ] } },
filter: { bool: { must } },     // ← not a valid top-level search-body key
```

OpenSearch rejects the body, the `catch` at `:164` fires on **every** Ask, and it silently degrades to `bm25Fallback`. The log line says so: `'Hybrid search failed, falling back to BM25'`.

Three independent confirmations:

1. Asked *"How should I pick a data store?"* against a corpus containing *"Decided to use PostgreSQL instead of MongoDB… need strong consistency and complex joins."* A perfect semantic match. Result: **`"citations":[]`**, "the notes don't contain information about how to pick a data store." Rephrased lexically as *"Why did I choose PostgreSQL over MongoDB?"* → answered correctly. That asymmetry is the signature of keyword-only retrieval.
2. `GET /thoughts/{id}/related` — pure k-NN, no fusion — returns `{"related":[],"count":0}`. Vector search returns nothing, ever.
3. **Root cause, deeper than the query bug:** nothing in the repo ever creates the index mapping. `grep -r "knn_vector\|indices.create"` hits only `design/`. Without a `knn_vector` mapping, `embedding` is a plain float array and k-NN cannot work **even if the query were fixed**. Additionally `config.ts:16` declares `EMBED_DIMENSIONS = 1024` while `titan-embed-text-v1` emits **1536** — and that constant is referenced nowhere, so nothing catches the mismatch.

**Impact**: ~$175/month is being paid for a vector database that has never served a vector. `README.md:41` ("Hybrid search combines BM25 keyword matching with semantic vector embeddings") is not true today.

**Fix**: (a) create the index with a `knn_vector` mapping at the correct 1536 dims — a bootstrap step is missing entirely; (b) move `filter` inside the `bool` clause or use `post_filter`; (c) make the fallback emit a metric and log loudly instead of silently degrading. Reconcile or delete `EMBED_DIMENSIONS`.

### 2. Custom metrics cannot be published — the monitoring is decorative

`compute-stack.ts:86` defines `cloudWatchMetricsPolicy`. It is attached to **exactly one** Lambda:

```
compute-stack.ts:274   this.graphLambda.addToRolePolicy(cloudWatchMetricsPolicy);
```

The other five that call `emitMetrics` — capture, ask, indexer, conversations, thoughts — have no `cloudwatch:PutMetricData`. Every custom metric silently fails.

The dashboard (`monitoring-stack.ts:185–218`) and the `SearchHitCount` alarm (`:341–353`) both read `namespace: projectName` metrics that **can never exist**.

**This is why finding #1 survived undetected.** The alarm built to catch broken indexing was structurally incapable of firing.

**Fix**: attach the policy to all six Lambdas. One line each. **Highest-leverage change in the repo** — do this first, because without it you cannot verify any other fix worked.

### 3. Every note self-deletes after 365 days

- `capture/index.ts:101` — `ttl: { N: (now/1000 + 31536000) }` on every item. `31536000 / 86400 = exactly 365 days`.
- `storage-stack.ts:107` — `timeToLiveAttribute: 'ttl'` arms it.

DynamoDB is the **sole** source for the Feed (`thoughts/index.ts`) and `/export`. OpenSearch and S3 have no matching expiry, so each note vanishes from the Feed and from Obsidian export on its first anniversary while remaining searchable, citable, and a graph node forever.

For a system whose premise is permanent memory, this is the most serious bug in the repo. **Oldest live notes are ~6 months old — roughly 6 months before data starts disappearing.**

**Fix**: stop writing `ttl` in `capture/index.ts:101`. Remove `timeToLiveAttribute` from the table. Existing items keep their attribute — clear it with a one-off scan.

### 4. Notes over 1,000 characters are silently truncated

- `capture/index.ts:92` — `text: { S: sanitizedText.substring(0, 1000) }`
- `packages/shared/src/utils/validation.ts:4` accepts **50,000** chars, and `capture/index.ts:50` advertises that limit in its own error message.

Both user-facing read paths serve the truncated field and **neither imports S3** (verified: `grep -c "S3Client"` → 0 in both `thoughts/index.ts` and `export/index.ts`). The full text exists in S3 but no read path reaches it.

Combined with #3: after a year the truncated copy is deleted and the full copy in S3 is orphaned.

**Fix**: either store full text in DynamoDB (400 KB item limit is ample for 50 K chars) or have the detail/export paths read S3 via the `s3Key` already stored at `capture/index.ts:99`.

### 5. Deleted and edited notes persist in the search index **[live]**

Reproduced: captured a note → confirmed indexed → `DELETE` → `204` → vanished from Feed → **still returned by `/search`**.

`thoughts/index.ts` has no OpenSearch client, and `compute-stack.ts:251` grants `thoughtsLambda` only `grantReadWriteData` — no `aoss:APIAccessAll`. Every other index-touching Lambda gets an explicit grant (indexer `:196`, ask `:223`, graph `:278`, conversations `:311`, search `:357`). It is **structurally incapable** of deleting the index doc.

Deleted note text stays searchable, citable, and a graph node permanently. Same for edits: Ask keeps citing stale text.

Independently re-confirmed from a third path: the graph reported **34 nodes** while the Feed held 32 — two deleted audit test notes still present.

**Fix**: enqueue a delete/reindex SQS message from the thoughts handler (reuses the existing indexer path), or grant `aoss:APIAccessAll` and delete inline. The SQS route is preferable — it keeps index writes in one place.

> **Residue from this audit**: two test notes (`wombat-glyph-*`, `zzqqx-unique-marker-*`) are orphaned in OpenSearch and cannot be removed via the API until this is fixed. Two S3 graph cache entries (`month=2026-01`, `2026-02`) are also mine.

## P1 — High

### 6. The galaxy renders fabricated topology **[live]**

`graph/index.ts:431`, in the DynamoDB fallback path:

```js
const embedding = Array(1024).fill(0).map(() => Math.random() - 0.5);
```

Random vectors feed K-means, cosine edges, and theme labels — then get cached to S3 and returned as `200` with `metadata.algorithm: 'k-means'`. No flag, no metric, no UI signal.

Live evidence, and the diagnostic that isolates it:

| Request (fresh cache key) | Edges |
|---|---|
| `minSimilarity=0.0` | 79 |
| `minSimilarity=0.7` | 79 |
| `minSimilarity=0.85` | 79 |
| `minSimilarity=0.99` | 79 |

Threshold-insensitive **and** saturated at the per-node cap ceiling (32 × 5 ÷ 2 = 80, `buildEdges:470–486`). Real embeddings thin out monotonically as the threshold rises; random 1024-dim vectors have near-zero pairwise cosine, so all pairs clear 0.0 and none clear 0.7. This is the signature of the random fallback.

Also: `/graph?level=overview` returned **three themes all labelled "Miscellaneous"** with `totalEdges: 0`. "Miscellaneous" is the hardcoded failure string at `graph/index.ts:299`. The labeller calls `anthropic.claude-3-5-haiku-20241022-v1:0` (`:276`) — hardcoded, bypassing the shared `MODELS` config, and **past Bedrock EOL** — so every label silently fails.

**Fix**: delete the random-embedding fallback and fail loudly (503 + metric). Route the labeller through `MODELS.FAST`. A note missing an embedding should be excluded from the graph, not fabricated into it.

### 7. Graph cache key omits `minSimilarity` **[live]**

`graph/index.ts:881`:

```js
const cacheKey = `graph/${user}/${params.month || 'all'}-v2.json`;
```

`minSimilarity` is parsed at `:876` and passed to `buildEdges` at `:1042`, but is absent from the key. With a 1-hour TTL (`:909`), a documented query parameter is silently inert for up to an hour. This also produces misleading `edges: 0` readings that make working code look broken — and plausibly motivated visual rework that wasn't needed.

**Fix**: include `minSimilarity` in the cache key. ~2 lines.

### 8. Constellation edges are hashtag overlap, not semantics

`CanvasRenderer.ts:251` — `this.edges = edges.length > 0 ? edges : generateHeuristicEdges(thoughts)`. The heuristic (`:71–113`) scores **5 points per shared tag**, +2 for same type, and a small importance term. `grep embedding CanvasRenderer.ts` → **0 hits**.

So when the backend returns no edges (routinely — see #6, #7), "connected ideas" means "shares a hashtag." `README.md:57` promises "connected thoughts"; `ThoughtDrawer.vue:114` renders the derived number as a `% ` similarity.

**Fix**: acceptable as a labelled fallback, not as a silent substitute. Show provenance in the UI ("linked by #tag" vs "semantically similar") and stop rendering heuristic scores as percentages.

### 9. Confidence and "% match" are fabricated signals **[live]**

- **`calculateConfidence`** (`search.ts:247`) is the mean of raw fused BM25 scores, capped at 0.95. Live: *"What is 2+2?"* returned **`confidence: 0.95`** while citing three unrelated DynamoDB notes. The most confident answer the system produced was to a question it had no business answering.
- **`normalizeScores`** (`search.ts:254`) is min-max over the citation list, so the **lowest-ranked citation always renders 0%**, and a single-citation answer renders 0%. Live: the correct PostgreSQL answer cited one note at `score: 0`, which `AskModal.vue:131` prints as `0% match`.
- **`MIN_CITATION_SCORE = 0.3`** thresholds an unbounded BM25-derived score, so prior audit finding #11 was never actually fixed. (It does bite on weak matches against old notes via the recency term, but is not a relevance gate.)

Citations are the stated trust mechanism (`README.md:322`). These signals are noise.

**Fix**: drop min-max normalization for citations — show rank, or a calibrated score, or nothing. Replace `calculateConfidence` with something honest (e.g. top-hit margin) or remove the number.

### 10. Citations are dead ends

`AskModal.vue:122–133` and `ChatView.vue:224–237` render citations as non-interactive `<div>`s. You cannot click a source to reach the note it came from. `preview` is hard-truncated to 300 chars (`search.ts:235`) and clamped further by `line-clamp-2`.

Note: there is **no `GET /thoughts/{id}` route** (`api-stack.ts:199` exposes only PUT + DELETE), so this needs a new route and handler branch — not pure frontend wiring.

**Fix**: add `GET /thoughts/{id}`, then make the citation card open the full-thought modal that already exists in `FeedView.vue:474–532`.

### 11. `GET /thoughts?type=…` is not user-scoped

`thoughts/index.ts:62–67` — when `type` is supplied, the query switches to `IndexName: 'gsi1'` with `KeyConditionExpression: 'gsi1pk = :typeKey'` and **no user predicate**. The default branch (`:80`) correctly scopes by `pk = user#...`.

Currently latent — the authorizer maps everything to a single `dev` user — but it is a cross-tenant read the moment multi-user is enabled, and multi-user credential support was already added in the last commit.

**Fix**: add a `user` filter expression to the GSI branch, or include `user` in the GSI partition key.

Four things only surfaced by deploying, each of which invalidated a plausible-looking fix:

1. **`aoss:DeleteDocument` does not exist.** CloudFormation rejected it. `aoss:WriteDocument` already authorizes deletes — confirmed by probing the API with a scratch policy.
2. **OpenSearch Serverless rejects an explicit document `_id`** on index operations (`Document ID is not supported in create/index operation request`). Deletes must resolve the real `_id` by search. This also means **`processConversation` has never successfully indexed** — it passes `id: conversationId` at indexer:553 and has been failing since February. Logged as new finding 18 below.
3. **`term` cannot match `id`.** With no index mapping, dynamic mapping makes `id` analyzed text; ids like `t_c75f…-…` tokenize on `_` and `-`. The `.keyword` subfield is required. This is a direct downstream consequence of finding 1.
4. **Serverless has a ~10s index visibility lag.** A delete issued right after capture found nothing and silently orphaned the document. The indexer now retries with backoff (0/5/10/15/20s) and throws if still not found, so SQS retries rather than declaring false success.

### New finding 18 — conversation indexing has never worked

`indexer/index.ts:553` indexes conversations with `id: conversationId`, which Serverless rejects. CloudWatch shows the same conversation reprocessed repeatedly in February with no success line. Chat history is therefore absent from the search index, so `/ask` can never surface `conversationHits` despite `ask/index.ts` having code to build them. Fix: drop the `id` parameter and let deletes/upserts resolve `_id` by query, exactly as thoughts now do.

### Direct confirmation of finding 1

CloudWatch caught the indexer's own words, which settles the vector-search question at the mapping level:

```
ERROR Failed to find related thoughts: ResponseError:
  [query_shard_exception] Reason: failed to create query:
  Field 'embedding' is not knn_vector type.
```

Querying the live mapping confirms it: `embedding: {"type": "float"}`. Not `knn_vector`. Vector search cannot run.

### Bug introduced and fixed during cleanup

While purging audit test data I triggered a latent bug worth recording: `processThought`'s `UpdateItemCommand` (indexer:488) upserts, so deleting a thought while its indexing is in flight **recreates the row** with only derived fields — an id-less, text-less ghost the Feed renders as an empty card and no API call can address. I created 18 such rows, removed them directly in DynamoDB, and added `ConditionExpression: 'attribute_exists(pk)'` so a delete now always wins the race.

Post-cleanup state verified: **32 notes in the Feed** (original demo data), zero ghosts, zero orphaned index documents, all endpoints 200.

### The defect that blocked everything: `_mapping` 404s on Serverless

`ensureSearchIndex` validated an existing index with `indices.getMapping`
(`GET /<index>/_mapping`). **OpenSearch Serverless returns 404 for that path even
when the index exists and is healthy**, so validation threw
`incompatible mapping` forever once the index existed — a deadlock that blocked
all indexing. `GET /<index>` returns the same `mappings` block and works.

This was genuinely confusing to diagnose because the two probes disagree:
`_cat/indices` reported the index present with 0 docs while `_mapping` reported
404. `GET /<index>` resolved it and showed the mapping was in fact perfect.
`validateExistingMapping` now also throws on an unreadable mapping rather than
treating an empty body as a pass — failing open there would let a float-mapped
index quietly serve BM25-only results, which is the exact defect this module
exists to prevent.

### Corrections to earlier findings

- **Finding 1's mapping claim was a symptom, not the cause.** `embedding: float`
  was not a mistake anyone made — **nothing in the codebase ever created the
  index.** It was auto-created by the indexer's first write, and dynamic mapping
  infers `float` from a JSON number array. Any fix that only patched the live
  index would have regressed on the next recreate.
- **`EMBED_DIMENSIONS = 1024` had always been wrong** (Titan v1 emits 1536). It
  was unused, so it never broke anything; the v2 upgrade made it honest.
- Finding 9 was worse than recorded: `citation.score` was min-max normalized
  *within the result set*, so the top hit always rendered as exactly `100% match`
  and a single-citation answer was 100% by construction.

### Left undone in step 3

- **The `reindex` message path cannot bootstrap an empty index.** It calls
  `deleteThoughtFromIndex` first, which throws after 5 attempts when the document
  is absent, so every message DLQs. Recovering the index required the plain
  `thought` path instead. A `reindex` that tolerates a missing document (or an
  explicit backfill entry point) would make disaster recovery a one-liner.
- **No idempotency on the `thought` index path.** SQS is at-least-once, so a
  redelivery writes a second document for the same logical id. Serverless forbids
  client-supplied `_id`, so the natural fix — deterministic ids — is unavailable;
  it needs delete-then-write, or dedupe at query time.
- **`GET /thoughts?type=…` is still not user-scoped** (finding 11). Untouched by
  step 3 and the one remaining item with a security dimension.
- Findings 8, 10, 14, 15, 16, 17 — unchanged, out of step 3's scope.

**Step 4 — Decide direction (discussion)**
- Drop OpenSearch for in-memory brute-force cosine? 10 K notes × 1536 dims × 4 B = **61 MB**; `cosineSimilarity` already exists in `graph/index.ts:103`. Saves ~$175/mo and fixes semantic search.
- Feed Ask full note text instead of 6 × 150-char fragments (~225 tokens) with `max_tokens: 300`. At ~1¢/query on Sonnet, this improves answers more than any retrieval tuning.
- Mac app: capture-only companion, or delete?
- Expose the corpus as an **MCP server**? Highest-leverage repositioning — the model does agentic search, a real global hotkey comes free via the desktop client, and "my notes, in my AWS account, queryable by any AI client, with citations" is defensible in a way another notes UI is not.

## Method and limitations

- 12 independent review passes (product flow, retrieval, architecture, graph, cost, tests, macOS, docs honesty, bloat, security, market, model capability), each re-checked by an adversarial verifier instructed to refute it. Claims that failed verification were dropped or corrected.
- Findings marked **[live]** were reproduced against the deployed dev API.
- **Limitation (since resolved)**: at audit time AWS credentials were invalid, so CloudWatch logs could not be read, and the BM25-fallback diagnosis rested on code reading plus black-box behaviour. Credentials were later provided; the diagnosis was confirmed directly, and step 3 fixed it.
- **Limitation**: the deployed backend is slightly **older than the repo** — `indexingStatus` is absent from live responses, and the tiled LOD graph API is not deployed (the frontend runs the legacy adapter in `apps/web/src/api/graph.ts`). A redeploy may shift specifics, but not #1 or the missing index mapping, both present in current source.
- **Correction made during the audit**: the galaxy's `edges: 0` was initially read as proof that cosine code was dead. It is a stale-cache artifact (#7); forcing fresh computation yields 79 threshold-insensitive, cap-saturated edges — which points to the random fallback (#6) rather than broken math.
